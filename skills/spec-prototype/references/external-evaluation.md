# Evidence-backed external evaluation

Read when a user requests Impeccable scores, qualification or repeated design
evaluation. Ordinary co-design uses the existing quality Review. Numerical
scores are expert assessments of inspected work, not user-study results or a
guarantee that a future generation will be excellent.

## Freeze the evaluation before generation

Retain the source/version of the rubric, skill/Builder digest, raw brief,
product facts, declared platforms/themes, required tasks/states/content ranges,
viewports, tools, evaluator separation and pass threshold. Keep case-specific
expected answers and previous scores outside the executor context. Test both a
normal scene and a contrasting dense, mobile or recovery scene. An explicitly
delegated evaluation can choose reversible design details, but is not evidence
of a real customer's selection.

Use the actual Impeccable version available to the task. The researched version
is commit `cd12f8660e2dde57b9615c8a6b8ea674101f9cfc`:
[critique](https://github.com/pbakaus/impeccable/blob/cd12f8660e2dde57b9615c8a6b8ea674101f9cfc/skill/reference/critique.md)
and [audit](https://github.com/pbakaus/impeccable/blob/cd12f8660e2dde57b9615c8a6b8ea674101f9cfc/skill/reference/audit.md).
Read the scoring sections when applying this profile; do not infer numeric
anchors from the paraphrases below or silently substitute a newer rubric.

## Keep three judgments distinct

| Assessment | Dimensions | Evidence |
|---|---|---|
| Impeccable critique | Status visibility; real-world match; control/freedom; consistency; error prevention; recognition; efficiency; aesthetic relevance; recovery; help | Attempt tasks from visible cues, inspect decisions and recovery/return; integer 0–4 per applicable heuristic |
| Impeccable audit | Accessibility; performance; theming; responsive design; implementation integrity | Runtime/browser observations, computed styles, raw checks and contextual detector triage; integer 0–4 per dimension |
| Product design merit | Existing seven quality dimensions, with particular attention to composition, expressive coherence and signature transfer | Inspect actual-size work before rationale and verify the idea survives a contrasting task |

Preserve raw upstream scores. If a rubric assumes an unrequested feature such
as dark mode, note the resulting raw limitation and report a separately labeled
product-scoped assessment; never inflate the raw result or add a feature merely
to satisfy the scale. Apply upstream critique `n/a` only with a real scope reason
and renormalized denominator. Missing evidence is **unverified**, not `n/a` or 4.
An automated accessibility scan is not a full WCAG conformance assessment.

For “near full in every dimension,” predeclare a strict profile: every applicable
raw scored dimension must attain 4/4 in the inspected scope; all seven product
quality dimensions must be supported; required tasks/accessibility assertions
must pass and no P0/P1 remains. If the requested profile cannot be applied without
inventing scope or making unsupported claims, report the exact unresolved
dimension. An excellent total alone does not meet this stricter request. A
different user-agreed threshold must be recorded before observing outputs.

## User-agreed product-scoped profile

When the user chooses product-scope qualification, freeze that agreement and its
rubric **before the qualifying generation**. Continue reporting upstream integer
scores independently; do not reclassify previous results as passes. A suitable
near-full profile uses the same fifteen dimensions with half-point resolution,
requiring every applicable dimension ≥3.5/4, all required checks passed, no issue
that materially obstructs a core decision/task/recovery/return, and evidence for
the seven product-quality dimensions including repeated generation.

For this separately labeled scale, 4 means the dimension's in-scope purpose is
fully supported by inspected evidence; 3.5 allows only minor localized friction
that leaves the task clear and complete; 3 or below reflects material friction
or a required evidence gap. A missing observation is unverified, never a bonus.
Use the finer scale only in this product-scoped assessment, not the raw rubric.

Keep the underlying design intent: status truthful across transitions; language
and choices understandable; authorized control/return reliable; conventions
coherent; known errors prevented appropriately; needed context recognizable;
frequent/return tasks efficient; expression purposeful; recovery retains work;
help appears where needed. Audit the agreed accessibility checks, observed
performance, requested themes/tokens, required responsive/content conditions and
implementation integrity. Unrequested undo, customization or dark mode cannot
become scope requirements merely because the raw top anchor mentions them.
Record actual residual issues and test limits; this is not certification, user
research or a guarantee about unseen products. Do not silently select this
profile when the user specifically requires the literal upstream result.

## Review without anchoring and without shortcuts

Where independent execution/review is available and authorized, give the
executor only the brief, skill and allowed raw materials. Give the design
reviewer the product brief, target and runnable evidence, withholding generation
rationale, previous scores and detector findings until its assessment is retained.
Run deterministic/browser checks separately and then reconcile evidence. Follow
the invoked tool's real availability and permissions; name any shared-context
assessment instead of calling it independent. A missing detector must be an
observed availability failure, not a guessed clean scan.

Inspect the primary task, incorrect input, relevant interruption/retry and later
visit. Capture narrow/wide/long-content states, keyboard focus/continuation and
reduced motion. Record screenshots, commands, raw results, exact target digest,
score anchors, observed weakness and limits per dimension. Respect mobile web
versus native scope. Tests for correct data alone do not establish discoverability;
screenshots alone do not establish behavior; expert walkthroughs are not user tests.

## Improve the skill, then regenerate

For skill qualification, preserve each failed run. Locate the cause in grounding,
method routing, composition development, specification, Builder instructions or
verification. Revise that reusable owner, retain the changed skill digest, and
have the executor regenerate in a fresh output scope. The evaluator/skill author
must not patch prototype output or send bespoke CSS/markup fixes to rescue it.
Builder may repair its own implementation within its declared boundaries; retain
first-pass and repaired evidence when assessing reliability.

Use the same raw brief, environment and tool permissions for baseline/candidate
comparisons. Add a contrasting product and repeat generation before claiming
transfer/stability. Report each run and dimension, including failures and cost
when measured. A single successful sample supports that sample only. Do not
revise a rubric after seeing results, hide failed trials, weaken assertions or
manufacture user preferences to close the loop. For an explicit sustained
qualification goal, continue the skill→fresh generation→review cycle within
authorized scope; ordinary discussion cadence is not a one-pass qualification cap.
